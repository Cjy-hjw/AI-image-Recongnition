## 体检项 1：模型权重大小 — 风险 低（且暴露更高层风险）

**结论**：模型 = ConvNeXt-Nano（分割骨干，14.9M）+ EfficientNet-B2（分类骨干，9.1M）+ 轻量头，合计约 **24.1M 参数量**。FP32 权重约 96MB、FP16 约 48MB。
（实测：`timm.create_model('convnext_nano', in_chans=1)` = 14.9M，`efficientnet_b2` = 9.1M。）

推理 batch 恒为 **1**（`model_runner.py:82-89` `preprocess_image` 单帧 `unsqueeze(0)`reshape 到 `img_size=512`，一次性 forward）。单帧 512×512×1 输入，FP16 autocast（`model_runner.py:92-138`），峰值仅数 GB，**32G 显存下余量巨大**，远不到 OOM 阈值。分类各头输出维度很小（`multi_task_model.py:68-180`）。

**但发现更高层风险**（见体检项 5）：`Dockerfile` **未把任何权重 COPY 进镜像**，`checkpoints/` 目录本地也不存在。权重缺失时 `build_model` 走随机初始化分支（`model_runner.py:70-75`），**输出一份"看起来正常"的垃圾诊断**——比崩溃更危险。

**建议**：
- 交付前把 `checkpoints/thyroidxl_merged_v2.pth`（+ `authenticity_model.pth` + SSCD + `calibration.json`）**COPY 进镜像**（现在 Dockerfile 一行都没有）。
- 云端验证：32G 显存下跑一次静态 + 动态批量，`nvidia-smi` 观察峰值显存。

## 体检项 2：惰性构建对 8000 探针的影响 — 风险 高（构建设计正确，但权重缺口的首爆点）

**两个关键问题的明确答案（基于代码追踪，非猜测）：**

### Q1：权重缺失时 /health 是否仍 200？ — **是，恒 200**
- `build_service_runner()`（`runner.py:108-123`）**完全不碰模型**，只解析参数、设 `state={"built": False}`，真正的 `build_model` 推迟到 `_ensure_built()`。
- `main()`（`app.py:159-178`）启动只调 `set_runner(build_service_runner())`，不加载权重 → 启动快、8000 端口立刻就绪。
- `/health`（`app.py:94-102`）只调 `tasks.task_summary()`（内存 dict 浅拷贝，`tasks.py:56-69`），**不查模型、不读磁盘、不碰线程池**。权重缺失不影响它。
- **结论**：即使 `checkpoints/` 全空，服务照常启动、`/health` 照常 200、`/call` 照常收活。平台探针不会因权重缺失而重启容器。

**但**：权重缺失时每次 `/call` 的推理会失败——
- `thyroidxl_merged_v2.pth` 缺失：`build_model` 只 `[WARNING]` 后随机初始化，**照常产出垃圾诊断**（`runner.py:153` → `model_runner.py:70-75`），任务 DONE、回调 200，评测拿到的是"合法但全错"的结果。
- `authenticity_model.pth` 缺失：**（R3 翻案后）** `build_auth_module` 不再硬报错——`gatekeeper_runner.py` 已改为 `except` 降级返回 None、置 `auth_skipped=True`，主诊断照常产出（依据赛道七真实性零计分，权重缺失不应拖垮整例）。~~此前为硬 RuntimeError 在 worker 线程抛出 → 每例零诊断~~（旧行为已废，保留存档）。

### Q2：首次 /call 模型加载期间 /health 会不会超时？ — **不会，恒 200**
- 模型加载发生在 **worker 线程**（`tasks.py:28-29` `ThreadPoolExecutor(max_workers=1)`），不在 event loop。
- `/call`（`app.py:105-147`）在 event loop 里只做入参解析 + `tasks.submit_inference`（丢线程池后**立即** return 200），模型加载是异步后台行为。
- `/health` 由 event loop 服务，**推理/加载期间 event loop 始终空闲** → `/health` 永远 200，连续 3 次探活失败重启容器的事件**不会触发**。
- worker=1 串行（`config.py:49`）正是为此设计：单卡 32G 显存下并发推理仍可能 OOM，且模型非线程安全，排队串行是唯一安全解。

**风险点同一处**：`_ensure_built` 的加载（建双骨干 + 载权重 + gatekeeper 三件重型对象 + dedup 编码 200 张训练图）是**同步阻塞**发生在 worker 线程内。单 worker 下，**加载期间后续 /call 只能排队**（status=PENDING），但 `/health` 不受影响。若平台在模型加载窗口内发来第二批 /call，只会排队不超时。**此设计是安全的。**

**建议**：无需改代码。云端首跑核对权重路径（`@云TODO` `runner.py:49-53`），确认 `AICOMP_WEIGHTS` 指向镜像内实际存在的权重。

## 体检项 3：批量推理 RAM/显存 — 风险 中

**动态全帧（max_frames<=0）内存代价**（`@云TODO` 标注处）：
- `load_nifti_frames`（`nifti_io.py:146-148`）`np.asarray(img.dataobj)` **把整个体积读进 CPU 内存**。
- `_write_dynamic`（`v21_output.py:297-308`）构造 `binary_3d` + `soft_3d` 两个**全帧序列** 3D 数组（`scatter_frames_to_full_length` 回填全帧，未抽中帧填 0）。
- 峰值估算（每病例，单帧图像数组 + soft3d float32 + binary3d uint8）：

| 原图分辨率 | 帧数 | 每病例峰值 |
|:---|:---|:---|
| 512×512 | 500 | ≈ **786 MB** |
| 1024×1024 | 500 | ≈ **3.1 GB** |
| 2048×2048 | 500 | ≈ **12.6 GB** |

- **内存泄漏**：未发现。`per_case` 的 `binary/soft_frames` 列表、`binary_3d/soft_3d` 每病例结束后出作用域被 GC 回收。`_process_case` 逐病例独立 try/except（`runner.py:192-216`），`frames` 列表也在病例内用完即弃。**无跨病例累积**。
- **64G 内存在几百病例下够不够**：典型 512×512 静态/动态（32 帧抽样）每病例仅几十 MB，几百病例串行足够。**仅当动态取全帧 + 高分辨率（≥1024）+ 长视频（≥500 帧）时**，单病例峰值可达数 GB；64G 下仍够，但若一个病例峰值 12.6GB（2048 全帧）需留意。

**显存**：动态逐帧 forward 峰值 = 单帧 512×512 batch=1（`case_pipeline.py:140-163`），关键帧张量只保留 1 帧（`case_pipeline.py:160-162`，注释明言"从 N 帧降到 1 帧，防平台显存上界 OOM"）。**32G 显存下逐帧 forward 峰值极低**，非瓶颈。

**建议**：
- 长视频高分辨率用例：显式设 `AICOMP_MAX_FRAMES` 抽样（默认 32），避免 `max_frames<=0` 全帧 + 高分辨率叠加。
- 云端验证：用 100+ 病例批量实测 `free -g` 观察 64G 内存水位、`nvidia-smi` 观察 32G 显存峰值。

## 体检项 4：单 worker 串行 vs 平台超时 — 风险 低

**结论**：线程池模型正确，长批量不阻塞 /call 与 /health。
- `tasks.py:28-29` `ThreadPoolExecutor(max_workers=1)` —— 推理全部在后台线程串行，event loop 只收请求/回调。
- `/call` 立即返回 200（`app.py:142-147`），**5 秒内响应要求稳定满足**（不做任何耗时操作，连 dataset_path 都不 stat）。
- `/health` event loop 服务，长批量期间恒 200。

**唯一注意点**：回调（`tasks.py:72-121`）在**整批跑完后**才发（`tasks.py:182`）。若单次 /call 的批量推理时长超过平台评测超时，回调迟迟不到 → 平台判超时。这是**批量规模**风险，不是并发阻塞风险。worker=1 下若平台并发发多个 /call，后续任务排队（status=PENDING），不阻塞前序，但总时长累加。

**建议**：云端首跑记录单批耗时，确认小于平台评测超时；若批量过大考虑拆批（但注意 worker=1 串行，拆批只是降低单批时长）。

## 补充 · 训练侧按 32G 规划（2026-08-11 误判已随 2026-08-12 实测定稿回拨）

**推理侧无风险**（上文已证：batch 恒 1、单帧 512² FP16、24M 参数，峰值仅数 GB ≪ 32G）。**规划要点**：三头 + 混训的 batch / 分辨率 / AMP / 梯度累积按平台实际 **32G** 规划（**2026-08-11 曾按下行误判口径"实测前取保守 14G、不是 32G"重算，现推翻**——08-12 容器内 `nvidia-smi` 实测定稿 32G，A800 80G 同量级参考，A800 上能跑的训练在本平台大概率也能跑）。规划要点：
- 训练 batch 需按 32G 实测定档（三头参数量极小，压力在主干 + 混训；必要时上**梯度累积**补等效 batch）。
- 平台 5090 = Blackwell sm_120，强制 CUDA ≥ 12.8（官方镜像全为 cuda12.8）。
- 队友那台容器显存更大可借用，或向组委会申请追加资源。
