## §2026-08-14 第二次真训 · 两个未解现象的调查过程（对应总纲 §6）

> ⚠️ **本节记调查过程与已否定的假设,当前状态与下一步以总纲 §6 为准。**
> 留存价值:下面三个假设都是**实测否定**的,compact 后极易重走。

### 现象①：loss 双峰

首个 epoch 日志(batch_size=16,每 20 step 一条):
```
step 0   loss 5.653   (10:40:55)
step 20  loss 5.322   (10:40:57)   ← 距上条仅 1.6s
step 40  loss 4.972   (10:41:31)   ← 距上条 34s
step 60  loss 0.907   (10:41:50)   ← 突然掉到 0.9
step 80  loss 4.643   (10:42:03)   ← 又回到 4.6
step 100 loss 0.813   (10:42:39)
step 120 loss 4.970   (10:42:58)
```
在 **~5** 与 **~0.8** 两个**分离值域**间跳,非连续噪声。**根因未知。**

**已否定的三个假设(均实测,勿重走)**:
1. ❌ 「某些 batch 临床标签全缺失 → masked loss 归零」——临床列缺失率约 17%,batch=16 且
   `shuffle=True`,全缺失概率 `0.17^16 ≈ 0`,不可能每几十步复现一次。**概率否定。**
2. ❌ 「ETE 极端类别不均衡致 ete 子损失大跳」——config 实测 `ete_class_counts: [3906,267,67,5]`
   (血管仅 5 例)、`ete_cb_beta=0.99` → CB 权重血管:无 = **20.4:1**,四头按 λ=1.0 硬外挂到总 loss,
   看起来很像元凶。**但按真实分布采样 20000 个 batch 实测**:ete 子损失
   `mean=0.137 sd=0.024 全幅仅 0.43`,且是**单峰**分布(直方图集中在 0.126-0.147 一簇);
   含稀有类与不含的 batch 均值差只有 **0.02**。**远不足以解释 4.0 的双峰间距。**
3. ❌ 「`--mock-labels` 冒烟没测出来,说明是环境问题」——mock 喂的是 `torch.rand()` **纯随机噪声图**
   (`scripts/train_official.py:188`),**完全不经过** `official_loader` 的读取路径、xlsx 解析、
   `.dcm`/`.nii.gz` 解码。它只验张量形状/梯度连通/不炸 NaN(即代码注释说的"管道数值健康")。
   **双峰是真实数据独有的结构性现象,mock 结构性造不出来。**

**为什么之前查不出来**:总 loss 是 24 个子损失经 SLR/FAMO **动态加权**后的标量,
**从它反推组成在数学上不可能**;而 `train_batch` 返回的 `loss_dict` 在 `run_official_epoch` 里
被**直接丢弃**。

**诊断手段(已加)**:`_step_diagnostics()` 把 24 个 `loss_*` 分项 + 6 个 `n_valid_*` 计数写进
JSONL 的 `extra=`。**`n_valid_*` 必须单独记而非旁推**:masked CE 在该头 valid 全 0 时返回
**精确 0**,与"损失已收敛到 0"在日志里长得一模一样——而"某头是否真的在受监督"正是本轮头号判据
(列名命中 ≠ 取值解析成功 ≠ 有监督样本)。

### 现象②：步耗时抖动 22 倍 + 动态 .nii.gz 报 `invalid block type`

20 step 耗时在 **1.6s ~ 36s** 间跳。同期云 agent 报某动态 `.nii.gz`(shape `1618×1216×360`)
nibabel 能读 header 但解压报 `invalid block type`。

**两种可能修法相反(2026-08-14 当时未定;2026-08-15 已定为 B,见本节末尾「结案」框)**:
- **A 文件真损坏** → 加载时跳过这些样本即可
- **B 文件完好,是我方读法炸了** → **跳过样本完全无效**,必须改代码

**B 有独立先验证据**:`official_loader._read_nifti_frame_gray` 对**每个样本**调
`load_nifti_frames(path, max_frames=-1)` 即**全量解码整段**(该模块 docstring 自述的已知雷)。
该文件 `1618×1216×360` int16 解压 **1.32GB**,而 `configs/thyroid_config.yaml:7` 的
`num_workers=12`(仅 `--smoke` 归 0,见 `scripts/train_official.py:453`):

| num_workers | 若同时命中动态样本,瞬时内存 |
|---|---|
| 0 | 1.32 GB |
| 4 | 5.3 GB |
| **12(当前默认)** | **~15.8 GB** |

加上 batch 内其它样本、pin_memory、主进程,64G 下是明确的内存压力路径,
而 `invalid block type` 正是 zlib 在流被打断时的典型表现。**这同时也解释了耗时抖动。**

⚠️ **若真因是 B 却按 A 处理,炸弹会留到 35 epoch 正式训练才响,届时静态样本一并挂。**

**🔴 云 agent「174MB 压缩率极低说明损坏」的推断已证伪**:`1618×1216×360 = 7.08e8` voxel、
int16 未压缩 **1.35GB**,压到 174MB 是 **7.8:1**,对超声视频完全正常;其引为基准的
"正常 5-10MB"是**二值 mask** 的量级(0/1、大片全零、压缩率 100:1+),两者本就差两个数量级。
→ **文件大小不是损坏证据,唯一实证只有 `invalid block type` 一条。**

**诊断手段(已加)**:`scripts/data/diag_niigz_integrity.py` —— 纯 gzip 层顺序流式解压(绕开
nibabel,不 seek、逐块丢弃);**能读到底=B,中途失败=A**。

（**2026-08-15 结案**：A/B 二分已终结,定为 B,非文件损坏。修复 = `scripts/data/preextract_dynamic.py`
预抽取 PNG 缓存。训练消费的从来只有 loader 读帧后立刻 `_resize_*` 出的 512×512 uint8,
缓存存的就是 resize 之后、增强之前的那一张,插值方式与 loader 逐位一致,**数值等价非近似**
(主会话对拍 5 种尺寸逐位一致)。训练期不再碰 `.nii.gz`;`diag_niigz_integrity.py` 保留作
通用 gzip 完整性工具。量级与易错点见 `docs/项目现状总纲.md` §6;§2.1 的耗时抖动也随之消除。）

### 同轮 Gate2 审查（两路并行）

**修了 3 个真 bug**:
1. **JSONL 写出裸 NaN**:`json.dumps` 默认 `allow_nan=True`,`{"loss_seg": float("nan")}` 输出
   `{"loss_seg": NaN}` —— **非标准 JSON**,Python 宽容能读但严格解析器(评审脚本很可能 Go/Java)
   **拒收整行** → 撞 V2.1「未能读取到指定日志文件…可能被标记为可疑对象」。而 NaN 在本项目是
   **预期会出现**的(损失模块自带 `torch.isnan` 守卫、ETE focal 在 p_t=1.0 实测产生过 NaN 梯度),
   35 epoch × 24 分项撞上是迟早的事。已在写入层 `_drop_nonfinite` 丢弃——**不填 0**,因为填 0 会把
   "这项炸了"伪装成"收敛得很好"。
2. **`vox_offset` 硬编码 352**:带 extension 的 NIfTI 文件 `vox_offset > 352`(实测某文件 608),
   硬编码会把合法文件误报成 TRUNCATED。已改读 header @108 真值。
3. **尾部追加垃圾字节**:完好 gzip 成员后若跟非 gzip 字节,`gzip.read` 会抛 "Not a gzipped file",
   导致**完好文件被判损坏** → 跳过其实能用的样本。已加回退:只解第一个成员。

**驳回 2 条误报(记此防后人重走)**——两条都是"agent 声称验证但结论相反",若采信就会去"修"
不存在的 bug:
1. ❌ 「`default_collate` 对 dict 里的 int 只做浅拷贝,不合并成 tensor,致 `n_valid_*` 恒等
   batch_size、字段失效」——**实测**:8 个样本 3 个 valid=1,得 `tensor([1,0,0,1,0,1,0,0])`、
   `sum().item()=3` **正是真实有效数**,不是 batch_size 8。字段语义没问题。
2. ❌ 「`n_decomp` 恒为 0,不能定位损坏位置」——agent **只用小文件测就外推**。gzip 在成员末尾
   才校验 CRC,故小文件(<1 chunk)一次解完才发现错、恒为 0;**大文件实测** 54MB 压缩流在 90% 处
   损坏得 `n_decomp=58,720,256`。**官方文件正是 1.35GB 量级,该数有定位价值。**

**验证**:11/11 nii.gz 回归(4 种 dtype 与 nibabel 逐字段一致 + 3 种损坏形态仍被抓 + 2 个修复项生效)、
820 collected / 819 passed + 1 skipped、冒烟 EXIT=0。

### 🔴 第13轮云端核实：定位 header=1 关键 bug（2026-08-13）

**根因**:`parse_annotation_xlsx`(`official_loader.py:264`)读 xlsx 时**没传 `header` 参数**
(默认 `header=0`),而官方 xlsx 是合并单元格表头、真实列名在第2行(0-based row=1);`header=0`
把分组标题当列名,导致 `_FIELD_ALIASES` **全部**临床列候选名零命中(不止 tirads)——四头训练本会
静默 `valid_*=0`、全程不报错。

**为什么此前从未被发现**:候选列名此前全部基于"表头字符串本该是这些值"的静态推测,

## §分割护栏 · 判据两版被实测证伪的全过程（对应总纲 §6）

2026-08-16 backlog #127 内，护栏判据改了三版。**结论在总纲，本节存证伪细节**，
供日后有人想"简化"回前两版时回查。

### v1：`val_dice < 0.05` @ep12 —— 会误杀

hard dice 先 `p>0.5` 二值化，而真实病灶掩膜只占 512² 的 **0.1%~3%**
（静态 M 掩膜实测 20-90px）。分割**确实在学**但前景 logit 尚未越过 0 的阶段
可持续很多 epoch，dice 全程恒 0 → 早期用 dice 设硬门必然误杀。
误杀代价 = 白费一次 1-2h 人工审核上传窗口 + 一轮 24h 机会。

审查第 4 路据此建议放宽到 ep25/0.01，方向对，但它的标定实验用的是**密度 0.4 的
随机掩膜**（与真实 0.1-3% 差两个数量级），且其 `step0 max=0.865` 与云端实测的
`max=0.4463` 直接矛盾（初始化路径不同）。**用错的标尺调阈值不如换标尺。**

### v2：`spread = p_max − p_mean < 0.01` —— 实测 3/8 场景判错

设计初衷是抓上一轮"处处 0.445"的指纹（spread=0.0009）。主会话自查构造 8 个场景
实测（`tmp_main_spread_reverse_hole.py`）：

| 场景 | spread | v2 判定 | 真实结论 |
|---|---|---|---|
| 上一轮真实失败态（处处 0.445） | 0.0000 | abort | ✅ 该杀 |
| 常量图整体 >0.5（mask 全 1） | 0.0000 | abort | ✅ 该杀 |
| **有结构但整体偏低（max=0.45/mean=0.05）** | **0.396** | **放行** | ❌ **该杀**：`p>0.5` 仍全零、mask 全零、Sclin 仍 0 |
| **常量图 + 4 个异常像素** | **0.545** | **放行** | ❌ **该杀**：整体无结构 |
| 只有 1 个像素越过 0.5 | 0.940 | 放行 | ❌ 该杀 |

**根因**：`max` 与 `mean` 都是单点或全局标量，几个像素就能骗过 `max`。
第三行是最危险的失效方向 —— **假的安全感**，护栏看起来在工作实则形同虚设。

**独立审查用真实模型复现**：step10-20 间 6 次观测到 `spread≥0.01 且 mask 全零`，
首个窗口 spread=0.0105/max=0.4704。⚠️ 该脚本按 **step** 采样，step 与 epoch
非 1:1，**不能据此断言"落在 ep8 判定窗内"**（此推断我方一度写进 commit message，
已订正）；它证明的是"该失效态在真实模型上可达"，不是"必然出现在某个 epoch"。

### v3（当前）：`seg_over_half_frac >= 1e-4` —— 8/8 全对

`(pred_prob > 0.5)` 的像素占比，**直接就是**官方 IoU 匹配消费的量，与评分口径
同构而非间接代理。同样 8 个场景实测（`tmp_main_overhalf_judge.py`）全判对。

下界 `1e-4` ≈ 26 像素 vs 最小真实病灶 0.1% ≈ 262 像素 → **10 倍误杀余量**。

### 上界门（0.5）也被实测否掉

曾加过"占比 >0.5 → abort"防"全图判成前景"。**实测会误杀正常收敛的模型**：
随机初始化时输出普遍 >0.5（frac≈1.0），收敛到真值（1% 前景）**必然穿过 0.5**。
本地实测轨迹（BCE + 1% 前景 target）：

```
step0 1.000 → step10 0.926 → step20 0.555 → step25 0.219 → step60 0.0099
```

最后精确收敛到真值 0.0099，而上界门会在 step10-20 那段把它打死。
**高前景占比是收敛的必经之路，不是崩溃信号。** 真正"全图判前景"的崩溃态会
一直卡在高位不下来，由 ep20 的 dice 兜底门抓（frac 恒 1.0 → IoU 极低 → dice 上不去）。

### 判别力验证

回归测试 `tests/test_seg_guards.py`（31 项）含 `test_v2_hole_*` 两条反例锁 +
`test_no_upper_bound_constant_exists`。**9 路变异测试 9/9 全抓**（含"改回 v1 阈值"
"退回 v2 判据""删 NaN 门""边界 `<` 改 `<=`""缺失键当 0 处理"）。

⚠️ 变异测试中发现一条**测试自身的陷阱**：用 `range(SEG_FROZEN_EPOCH,
SEG_ABORT_EPOCH)` 写的遍历用例，在阈值被改回旧值后 **18 项全绿一个没红**
—— 常量一改遍历范围跟着变，测试永远自洽。故凡涉及阈值语义的用例，
**epoch/占比一律硬编码，不引用常量**。

**分割前向链 A/B/C 全程自训**（`schedule_official.py`）：新增两个常量并入 requires_grad

BN 正常更新；只解冻部分参数（如解 conv 留 BN）会落进 `tests/test_bn_freeze.py` 钉死的

🔴 **`requires_grad` 必须与 optimizer 参数集合严格对齐**（本项目已发生过的事故形状）：
`src/models/AGENTS.md:62` 记载 LoRA 参数"可训练但不在 optimizer 内 → 梯度跨 batch
**永不清零、累积至溢出**"。只设 `requires_grad=True` 而漏建 param_group，训练会**静默发散**。
`test_optimizer_covers_all_trainable_except_vclub` 是钉这条的既有防线。

**刻意不动的**：`prior_extractor`/`prior_mlp`/`adaptor_stage3`/`adaptor_stage4`/`cbm_head`
保持冻结 —— 最小改动达成目标，且避免 Stage2 崩塌四因同时齐发。

**连带改动**：`composite` 纳入 `val_dice`（此前 5 项分类均值完全不含分割，即便训起来
选模也不朝分割方向选）；`seg_prob_*` 三项进 JSONL；ETE focal 降压

**护栏落点**：`seg_over_half_frac`（`(pred_prob>0.5)` 像素占比）**ep≥8 且 <1e-4 → abort**；
dice 门降级为兜底（ep≥20 且 dice<0.02）、dice<0.10 仅 warn；NaN 门单独拦

- Gate1 八门 `EXIT=0`；`pytest` **890 passed + 1 skipped**（基线 840）；冒烟通过；
  Gate2 七轮审查；护栏 **9 路变异测试 9/9 全抓**。
- **梯度实测**：`loss_seg` 在 A/B/C 三阶段都给 `seg_backbone` **全部 142/142 个参数**
  非零有限梯度（解码器 |grad|≈119、主干≈14）；四头→分割链梯度仍**精确 0**
  （隔离未破坏）；fp16 下分割链 `|grad|max=5.5e-02`，离 65504 天花板十万倍以上。
- **本地显存对拍**（RTX 4060，冻结 vs 解冻）：增量随 batch **严格线性 = 每样本 +0.51 GB**，
  batch=16 外推增量 ≈ **+8.2 GB**；AdamW state 增量仅 +0.044 GB。

### 🔴 外推被云端实测打脸（方法论教训）

上面那条本地外推在**增量趋势**上没错，但叠加到"上轮冻结态约 11GB"这个**来路不明的
基数**上，得出"解冻后约 20GB、≥24GB 就要降 batch"的预期。
**云端真值是 8824 MiB（8.6GB）恒定** —— 预期偏高一倍以上。

→ 教训不是"外推错了"，而是**外推的基数本身没有出处**。那个 `0.692×batch+0.121`
斜率全仓仅出现一处、`git log -S` 查不到来源，且恰等于冻结态数值。
**增量可跨卡外推、绝对值不可，而绝对值一旦建立在无出处的基数上，连量级都不可信。**
此后显存一律以云端实测为准。

## §上云与运维事故 · 第五轮上云的两次误判（对应总纲 §6）

> 2026-08-17。总纲只留三条铁律，事故链与排查过程存此。

### 事故一：「替换同名目录」抹掉同级其他文件

**背景**：上云包 `cloud_upload_r5.zip` 按 `unzip -o` 语义设计——zip 内是**带相对路径**的
9 个文件（`src/training/*.py`、`scripts/train_official.py`、`configs/thyroid_config.yaml` 等），
在项目根 `unzip -o` 即**按文件合并**、不动其他内容。README 步骤 1 写明了这一点。

**实际发生**：走了人工上传 + 系统「检测到相同文件自动替换」。上传的 `src/` 目录只含
`dataset/` + `training/` 两个子目录，系统按**替换整个同名目录**处理 →
`src/models/`、`src/utils/`、`src/gatekeeper/`、`src/inference/` **全部被抹掉**。
本地第一版包实测 `src/` 下 **67 个 `.py`**、6 个子目录，事故后云端只剩 9 个文件。

🔴 **哈希核对没抓到**：`sha256sum -c SHA256SUMS.txt` 当时 **9 行全 OK**——
因为被删的文件**不在那 9 个清单里**。
**教训：哈希清单只能验"我列出的文件对不对"，验不了"有没有别的文件被连带删除"。**
→ 核验须补两条正交判据：`find . -name "*.py" -not -path "*/__pycache__/*" | wc -l`
（期望 ≈69）与 `python -c "import src.models.multi_task_model"`（缺任何一环当场 ImportError，
不用等起训）。

**恢复**：云端仍存第一版包 → 先恢复完整 `src/`（会把新版 7 个文件覆盖回旧版），
**再重放 9 个新文件**（顺序不可颠倒），最后哈希核对。全程未重新上传。

### 事故二：`mixup.py` 被误判为"漏传的改动"

排查缺失文件时，对比本地第一版包与当前仓库，`diff` 报出 **11 个**差异文件，
比上云包的 9 个多出 `src/dataset/augmentation/mixup.py` 与 `scripts/preflight_check.py`。
一度判断"有两个改动漏传了"。

**实为**：`mixup.py` 的 diff 是 `1,80c1,80`——**80 行换 80 行、行数一字不差**，
这是 **CRLF/LF 行尾符差异**的典型特征。`diff --strip-trailing-cr` 判定**内容完全相同**。
→ **比对文件差异必须先排除行尾符**，`1,Nc1,N` 且 N 相等时几乎必然是行尾符问题。

`preflight_check.py` 则是**真差异**（新增 UTF-8 强制 / 列名候选打印真实取值 /
权重"存在≠可加载"真解析），但它是**独立自检脚本、不参与训练**，不阻塞本轮。

   走 stdout 块缓冲要攒到 ep25 才刷新。epoch 指标现已进 JSONL（逐行 flush，不受缓冲影响）。
2. 🔴 **给云端的指令必须写死 `unzip -o`，不能是"把文件放进去"** —— 2026-08-17 走人工
   「替换同名目录」，上传的 `src/` 只含两个子目录，系统整个替换后 **`src/models`、
   `src/utils`、`src/gatekeeper`、`src/inference` 全被抹掉**（67 个 `.py` 只剩 9 个）。
   而 `sha256sum -c` 当时 **9 行全 OK** —— **哈希核对覆盖不到被连带删除的第三方文件**。
   → 核验须加 `find . -name "*.py" | wc -l`（期望 ≈69）+ `python -c "import src.models.multi_task_model"`。
3. **JSONL 是追加不是覆盖** —— 新一轮训练前先 `mv` 走旧的（用 `mv` 不用 `rm`，云端产物导不出来）。

⚠️ **`n_valid_*` 是 per-batch 计数**（batch=16 → 良恶性 15/16、位置/ETE/T 各 11-13/16、
TI-RADS 14/16、mask 16/16、is_main 13/16）。此前手册写的"预期 4784/4015/4740"是**全量口径**、
与该字段不是一回事，已致云端 agent 误报红灯，勿再用那组数当 per-batch 判据。
⚠️ **本地漂亮 ≠ 官方能拿分(08-15 上一轮的教训,对照基线已并入本节)**:那轮四头本地指标全部在学,但 val_dice 0.0007/pred_prob 全域<0.5 → 预测 mask 恒全零 → 官方 IoU 匹配零命中 → Sclin≈0。本地指标是金标准直接喂样本的口径,绕过 IoU 匹配环节;分割是整个评分的闸门而非"四项之一"。考证见 [订正史 §分割闸门](历史存档/总纲订正史.md)。
