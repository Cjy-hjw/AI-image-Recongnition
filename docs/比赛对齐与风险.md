## 二、为什么"必须先看官方数据"

比赛规则明确：**主办方统一提供数据**、**专属云环境训练**、**禁止外传/截图**。所以：

1. **基础两项(真实性/规范性)的真实标注只能来自官方** —— 真假人体、重复、拼接这些**取证样本**,公开数据集几乎没有对口的(我方现用合成引擎 `synthesis.py` 造训练数据 + CAT-Net/SSCD 预训权重打底),最终须用官方标注集验证/微调 `authenticity` 和 `tampering`。这是入场券,优先级最高。

2. **良恶性可先用公开数据预训、官方数据微调** —— TN3K 是纯分割集(malignancy 全 0)不能训分类;但选型报告已锁定 Stanford AIMI/Thyro-LMD(均带病理确诊良恶性),**可现在就预训出成熟分类基线**,8-01 官方数据到位后微调适配(自有模型组正是"成熟模型+微调"范式)。不再是"只能干等"。

3. **现在能做的只是"架构预演"** —— 用 TN3K + 公开数据集验证管线能跑通、不崩溃、指标能算出来。但真实性能数字要等官方数据才有意义。

### 关键未知（看到官方数据才能确认）
- 官方是否提供真假/重复/拼接的标注？标注粒度（图像级/像素级/bbox）？
- 良恶性标签形式？是否带 TI-RADS 概念级标注（决定 CBM 头能否监督训练）？
- 是否带分割 mask？分辨率、设备异质性如何？
- 数据量级、阴阳性比例？

## 风险总结

- **最高风险**：基础两项(真实性/规范性)不达标 → 直接出局。当前是传统算法骨架，**真实精度未知，必须用官方数据验证/升级**。
- **gatekeeper 统一软flag制度(2026-07-12 新增，P2启动前排查发现的一票否决红线风险)**：审计发现 gatekeeper 三条硬拒绝分支——`authenticity.py` 的 argmax 判定、`tampering_catnet.py` 的 CatNet↔copy_move 信任耦合、BAG 相位不一致——均存在"训练/阈值仅经合成数据验证、零真实域 FPR 实测，却直接一票否决"的风险，与此前 copy-move 27.3% 真实图误报被降级为软 flag 的先例同源。已按以下制度处理：① `authenticity.py` 分类结果降级为软 flag(仅审计,不驱动 REJECTED)，权重缺失/损坏仍硬报错(红线未动)；② copy_move/splice 与 CatNet 状态彻底解耦(不再因"CatNet 这次没崩溃"就把 27.3% 误报的几何判据升级为硬拒绝)；③ BAG 相位不一致加 `bag_hard_reject` 显式开关，默认 `False`(仅软 flag)。**统一闸门**：任何硬拒绝分支恢复"一票否决"资格，唯一条件是在官方真实干净 holdout 上完成预注册、带置信区间的 FPR 验收，不接受"加个置信度阈值"这类替代方案。详见 `docs/P2红线修复实施计划.md`、`docs/P2启动定论_Opus复核.md`、`src/gatekeeper/AGENTS.md` §1/§3。
- **次高风险**：误以为"分类做好就行"。实际上分类是决赛才重点考的核心项，但**进不了决赛(基础项挂)再好的分类也白搭**。
- **数据风险**：一切真实指标都依赖官方数据，现在的 TN3K 结果(除分割外)不能代表比赛表现。
- **联网禁令风险(答疑 Q26,新增)**：比赛期间禁联网/禁访问外网。公开预训数据集(Stanford AIMI 36GB/Thyro-LMD)、深度权重(CAT-Net/SSCD TorchScript)**必须赛前全部下好,随自有模型经"管理服务平台-个人工作台"上传(Q34)**,开赛后一律下不了。漏带=该能力降级到纯 NumPy/无预训。
- **动态图交付格式未知风险(2026-07-11 新增,entrypoint.sh 审计发现；2026-07-11 追加已加内容嗅探兜底)**：答疑 Q7/Q11/Q5 只给了"数据 JPG、静态+动态图"这个粒度,**从未明确"动态图"的具体交付形态**——是单个视频容器文件(mp4/avi/…)?DICOM 多帧 cine?还是一组按帧编号的 JPG 文件(既然静态图确认是 JPG,动态图完全可能是"JPG 帧序列"而非视频容器,两者对推理入口的 I/O 契约要求截然不同)?现有 `scripts/entrypoint.sh` 的分发白名单(`mp4|avi|mov|mkv|dcm|dicom`)是**纯工程假设,未经官方规格证实**——若实际交付是 JPG 帧序列或白名单外的容器格式,会被误判成静态图路由给 `predict.py`,大概率产出全批 ERROR(不会崩溃裸输出,2026-07-11 P0 修复已保证兜底,但会导致动态图任务 100% 拿不到有效预测,等同该项直接挂零)。**按 rules.md「先证后改」原则,现在不凭空猜测重写分发逻辑**——待 8-1 官方数据到位后第一时间用真实样本核实交付格式,若与当前假设不符,`entrypoint.sh`/`video_predict.py` 的输入加载层需要针对性改造(帧序列输入大概率需要新增"目录路径"这一入参形态,而非现在的单文件路径假设)。列为**开赛后第一时间必须验证**的清单项,不可拖延。
  - **当前处理状态(2026-07-11 追加)**：已给 `entrypoint.sh` 的扩展名分发加一层**内容 magic bytes 嗅探兜底**(DICOM offset 128 "DICM" 显式判定 + `file --mime-type` 识别 image/*、video/*)——① 扩展名与内容嗅探结果不一致时**以内容为准重新路由**并打印 `[WARNING]`,不再静默按可能错误的扩展名走;② 内容嗅探也判不出来时(既非 DICOM 也非常见图片/视频魔数)**直接判 ERROR 落 `result.json` 并 `exit 1`**,不猜测路由,避免误判成静态图导致该动态图样本 100% 丢失预测。**这只是"扩展名判断失效时更有韧性、失败更诚实"的工程加固,不等于解决了本条风险**——若实际交付真是"JPG 帧序列"(一组文件而非单文件),content-sniffing 对单个 JPG 帧只会嗅探出 `image/jpeg`,依然会被路由到 `predict.py`(单帧预测),不会自动拼装成 cine 送 `video_predict.py`;这类**全新输入形态的支持仍待 8-1 官方数据到位后用真实样本确认再实现**,不可凭空猜测。详见 `scripts/entrypoint.sh` 第 5 节注释、`scripts/AGENTS.md` §7、回归测试 `tests/test_entrypoint_dispatch.py::TestContentSniffFallback`。
  - **P1 输入覆盖扩容(2026-07-11 追加,与 Opus 战略咨询排定优先级一致,两轮)**：`docker-build-smoke` CI job(真实 `docker build` + 起容器,非模拟环境)此前只验证过标准 PNG/标准 MP4 两类输入。已扩容至 8 类真实容器验证场景:标准 PNG 静态图、标准 MP4 动态图、**DICOM 单帧**、**DICOM 多帧 cine**、**压缩 DICOM(JPEG baseline)**(用 `scripts/verify/gen_synthetic_dicom.py` 生成真正可被 `pydicom.dcmread()` 解析的合法 DICOM,而非仅有魔数字节的假文件)、**JPG 静态图**(官方确认的静态图交付格式,此前所有测试全用 PNG 构造从未验证过)、**非空损坏文件**(验证 `cv2.imread` 失败路径不裸崩溃)、**极端低分辨率(4x4)视频**(验证 resize+模型前向不因边界分辨率崩溃)。这一步把"DICOM 单帧/cine/压缩格式/边界分辨率/损坏文件/JPG"这几类**已知会出现**的输入形态从"未经真实容器验证的假设"转为"已用目标容器(torch==2.1.0)实测确认不崩溃"，缩小了本条风险的敞口。
    - **压缩 DICOM 是 Opus 战略审查(第二轮)发现的致命缺口**：真实超声 DICOM 绝大多数是 JPEG/JPEG2000/RLE 压缩，第一轮 P1 的 fixture 只测过未压缩 `ExplicitVRLittleEndian`——若压缩解码插件缺失，`ds.pixel_array` 会抛 `NotImplementedError`（被 `_load_dicom_cine` 的 `except Exception` 兜成 ERROR，不崩溃，但等于该动态图样本 100% 丢失预测，是"不崩溃但拿不到预测"这类比裸崩溃更隐蔽的风险）。已补 `pylibjpeg`/`pylibjpeg-libjpeg`/`pylibjpeg-openjpeg`（RLE 由 pydicom 内置 `rle_handler` 覆盖，无需额外包），版本锁 `numpy<2` 兼容区间（见 `requirements.txt` 注释——上游 `pylibjpeg-libjpeg`/`pylibjpeg-openjpeg` 从某版本起把 numpy 依赖改成 `>=2.0`，与本项目 `numpy<2` 硬约束冲突，已锁定兼容旧版本）。**验证边界说明**：本机开发环境 numpy 版本高于容器锁定值，无法在本地完整复现"容器内 numpy<2 + 锁定版插件"这个精确组合的解码路径，该组合的最终验证以 CI `docker-build-smoke` 的真实容器结果为准（与本轮更早发现的 torch 版本差异陷阱同一类教训）。
    - **仍不解决"JPG 帧序列"这一未证实形态**，这部分维持待 8-1 验证不变。详见 `.github/workflows/ci.yml` `docker-build-smoke` job、`tests/test_smoke_entrypoints.py::TestDicomInputPaths`/`TestJpegInputPath`/`TestCorruptedNonEmptyFile`。
  - **子进程崩溃零输出风险(2026-07-12 P2红线修复C级)**：`entrypoint.sh` 此前用 `exec python <script>` 把入口 bash 进程直接替换成 python 进程——若 python 侧发生原生崩溃(segfault)或被 OOM-killer 发 SIGKILL，替换掉的进程已不存在，没有任何存活进程能补写 `result.json`，评测方拿到零输出直接判零分(比任何数值误判都严重)。已改为前台子进程 + 父 shell `wait` + 崩溃兜底写 ERROR JSON，同时处理了信号转发(SIGTERM/SIGINT，避免容器优雅关闭时子进程变孤儿)与陈旧 `result.json` 误判(先移开旧文件，避免把上一次调用的残留结果误当成本次成功)两个配套问题。**诚实边界**：只接得住子进程自身崩溃/被单独 OOM-kill 两类情形，接不住整个 cgroup/容器被外部一并杀掉(此时父 shell 也不存在)——这类情形需容器编排层(k8s 存活探针+重启策略)兜底，不是本脚本能解决的问题，不可虚假宣称"已解决 OOM"。详见 `scripts/AGENTS.md` §7.1、回归测试 `tests/test_entrypoint_dispatch.py::TestSubprocessCrashFallback`。
